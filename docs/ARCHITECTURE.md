# ระบบจัดเวรแพทย์และจัดคิวโรงพยาบาล — Architecture

จิตฤดี ดวงดี · 27 ต.ค. 2569 · โค้ด: [github.com/JitrudeeDongdee/waka-crud](https://github.com/JitrudeeDongdee/waka-crud) · เดโม: [jitrudeedongdee.github.io/waka-crud](https://jitrudeedongdee.github.io/waka-crud/) · ตรงกับเวอร์ชัน v0.7.6

เอกสารนี้อธิบาย 5 เรื่องของระบบที่เริ่มจาก 15 โรงพยาบาลและขยายไปถึง 30 แห่ง ได้แก่ ขั้นตอนการทำงาน (BPMN), โครงสร้างฐานข้อมูล (ER diagram), โครงสร้าง server และ network ตอนขยายขึ้น cloud แผนย้ายจาก PHP/Laravel ไปเป็น Next.js + NestJS และข้อเสนอฟีเจอร์ถัดไป

**สรุปสั้น**

- **งานหลักคือการจัดเวรแพทย์รายเดือน** ส่วนคิวผู้ป่วยเป็นงานที่ใช้ตารางเวรต่อ ระบบจึงต้องรู้ว่าแพทย์คนไหนอยู่เวรเมื่อไหร่ และมีความเชี่ยวชาญอะไร
- **ผู้ใช้แต่ละบทบาททำได้ไม่เท่ากัน** (แอดมิน / แพทย์ / พยาบาล / เวชระเบียน) และเห็นได้เฉพาะข้อมูลของโรงพยาบาลตัวเอง ตรวจสิทธิ์ที่ backend ทุก request
- **รายละเอียดเทคนิคจัดการข้อมูลจำนวนมากพร้อมแหล่งอ้างอิง** อยู่ใน [LARGE-DATA.md](LARGE-DATA.md)
- **ขนาดข้อมูลไม่ใช่ปัญหาหลัก** ต่อให้ขยายถึง 30 แห่ง ก็ประมาณ 33 ล้านคิวต่อปี MySQL เครื่องเดียวรองรับได้ ถ้า index ถูกและแบ่ง partition ตามเดือน **ที่หนักจริงคือจอแสดงคิว** ที่ต้องอัปเดตพร้อมกันหลายร้อยจอ จึงควรใช้ WebSocket ไม่ใช่ polling
- **แพทย์มีส่วนร่วมในตารางเวร:** ส่งเวรที่อยากลง/ไม่สะดวกก่อนจัดร่าง และขอย้ายหรือแลกเวรกับเพื่อนได้เอง เพื่อนตอบรับแล้วสลับทันที ถ้าติดกติกาจึงส่งให้แอดมินเคลียร์ (ข้อ 1.3)
- **หัวหน้าแผนกจัดการแพทย์ได้เอง:** หน้า "แพทย์" แสดงความเชี่ยวชาญ เวรและชั่วโมงเดือนนี้ เวรถัดไป และคำขอลาที่รอของแพทย์ทุกคน เพิ่มแพทย์ใหม่และแก้ความเชี่ยวชาญได้ ตารางเวรและการเรียกคิวใช้ค่าใหม่ทันที
- **หน้าจอเดโมแต่ละกรณี (ข้อ 6):** ภาพหน้าจอจริงของทุกหน้าพร้อมคำอธิบาย ต่อท้ายเอกสาร
- **ข้อเสนอฟีเจอร์ถัดไป (ข้อ 5):** ให้ HR อนุมัติการลาแบบ 2 ขั้น, ประเภทการลาพร้อมกติกาแจ้งล่วงหน้า, วันลาคงเหลือ, แจ้งเตือน LINE/อีเมล และ audit log
- **ย้ายไป Next.js + NestJS แบบค่อย ๆ ทำ (strangler fig)** ทีละส่วน ระบบเดิมยังใช้งานได้ตลอด เริ่มจากหน้าเว็บก่อน แล้วค่อยย้าย API ทีละ module ส่วนที่เสี่ยงที่สุด (การออกและเรียกคิว) ย้ายเป็นอันดับสุดท้าย

## 2. ฐานข้อมูล (ER diagram)

ตาราง `users` เก็บบทบาท (`role`) และโรงพยาบาลที่สังกัด ถ้าผู้ใช้เป็นแพทย์จะผูกกับ `staff` ด้วย ทุกตารางที่เป็นข้อมูลของโรงพยาบาลจะมี `hospital_id` หรือผูกกับ `department` ที่มี `hospital_id` อยู่ เพื่อให้แยกข้อมูลได้ (multi-tenant แบบใช้ฐานข้อมูลเดียวกัน) และไม่เก็บชื่อหรือเลขบัตรผู้ป่วย เก็บแค่รหัสอ้างอิง (`patient_ref`) ที่ไปเชื่อมกับระบบ HIS ของโรงพยาบาล

### 2.1 จัดเวรแพทย์

![ER diagram จัดเวรแพทย์](diagrams/erd-roster.svg)

**ความสัมพันธ์**
- **โรงพยาบาล → แผนก → ช่วงเวร:** โรงพยาบาลหนึ่งมีหลายแผนก แต่ละแผนกกำหนดช่วงเวรของตัวเอง (`shift_templates` เช่น เช้า/บ่าย/ดึก) พร้อมจำนวนแพทย์ขั้นต่ำ และความเชี่ยวชาญที่ช่วงนั้นต้องมี
- **แพทย์ ↔ ความเชี่ยวชาญ:** แพทย์ (`staff`) สังกัดแผนกเดียว มีได้หลายความเชี่ยวชาญ และความเชี่ยวชาญหนึ่งมีได้หลายคน (many-to-many ผ่าน `skill_staff`)
- **เวร (`shifts`):** 1 แถว = แพทย์ 1 คน อยู่ 1 ช่วงเวรใน 1 วัน จึงผูกกับทั้งแพทย์และช่วงเวร เก็บเวลาเริ่ม/จบจริงไว้ด้วย (เวรดึกข้ามวัน) ใช้ตรวจกติกาพักและชั่วโมงต่อสัปดาห์
- **วันลา (`staff_unavailabilities`):** แพทย์หนึ่งคนลาได้หลายวัน วันละไม่เกิน 1 แถว มีสถานะรออนุมัติ/อนุมัติ/ไม่อนุมัติ และเก็บว่าใครขอและใครตัดสิน
- **บัญชีผู้ใช้ (`users`):** บอกบทบาทและโรงพยาบาลที่สังกัด ถ้าเป็นแพทย์จะผูกกับ `staff` หนึ่งคน (1 ต่อ 1) บทบาทอื่นไม่ผูก

ย้าย/แลกเวร และเวรที่อยากลง (กล่องเส้นประ = ตารางจากผังบน แสดงเฉพาะคอลัมน์ที่เกี่ยว)

![ER diagram ย้าย/แลกเวร](diagrams/erd-shift-requests.svg)

**ความสัมพันธ์**
- **เวรที่อยากลง (`shift_preferences`):** แพทย์หนึ่งคนมีได้หลายแถว 1 แถว = 1 ช่วงเวรใน 1 วัน ว่าอยากลงหรือไม่สะดวก
- **คำขอย้าย/แลก (`shift_change_requests`):** ผูกกับแพทย์ผู้ขอและเวรเดิมของเขาเสมอ ถ้าเป็นการแลก ผูกกับเวรของเพื่อนและตัวเพื่อนด้วย เก็บวันและช่วงเวรต้นทาง/ปลายทางตอนขอไว้ด้วย เพราะหลังสลับแล้ว `shifts` แถวเดิมเปลี่ยนเจ้าของ แต่ประวัติคำขอต้องยังอ่านรู้เรื่อง ถ้าหัวหน้าตัดสิน ผูกกับ `users` ของคนตัดสิน

### 2.2 คิวผู้ป่วยและสถิติ

![ER diagram คิวผู้ป่วยและสถิติ](diagrams/erd-queue.svg)

**ความสัมพันธ์**
- **คิว (`queue_tickets`):** แผนกหนึ่งมีหลายคิว เลขคิวรันใหม่ทุกวันแยกแต่ละแผนก คิวอาจระบุความเชี่ยวชาญที่ต้องการ (ไม่บังคับ) และพอแพทย์เรียกจะผูกกับแพทย์คนนั้น ไม่เก็บชื่อหรือเลขบัตรผู้ป่วย เก็บแค่รหัสอ้างอิงที่ไปเชื่อมกับ HIS
- **ตัวนับเลขคิว (`queue_counters`):** แผนกละ 1 แถวต่อวัน เก็บเลขล่าสุด ล็อกแถวนี้ตอนออกบัตรเพื่อกันเลขซ้ำเมื่อหลายตู้กดพร้อมกัน
- **สรุปรายวัน (`daily_queue_stats`):** แผนกละ 1 แถวต่อวัน สรุปจากคิวดิบทุกคืน ให้ dashboard และปฏิทินรายเดือนอ่านโดยไม่ต้องนับคิวดิบ

กรอบเส้นประ = ตารางจากข้อ 2.1 · ขีดคู่ = ฝั่ง "หนึ่ง" · ตีนกา + วงกลม = ฝั่ง "ศูนย์ถึงหลาย"

### 2.3 สิทธิ์ตามบทบาท (RBAC)

| ดูสถิติ | ✓ | | | |

**ตรวจ 3 ชั้น:** (1) ล็อกอินแล้ว (Sanctum token) → 401, (2) สังกัดโรงพยาบาลใน URL (`EnsureHospitalMember`) → 403 และ id ของโรงพยาบาลอื่นที่ใส่ใน URL → 404 (`scopeBindings`), (3) มีสิทธิ์ของ action นั้น และเป็นเจ้าของข้อมูลถ้าสิทธิ์จำกัดแค่ "ของตัวเอง" → 403 · มีชุดทดสอบสิทธิ์ 9 ข้อ (`AuthorizationTest`) ขั้นตอนการลา 7 ข้อ (`LeaveTest`) และการย้าย/แลกเวรกับเวรที่อยากลง 11 ข้อ (`ShiftRequestTest`)

**ผู้ใช้ทดลอง:** เดโมให้เลือกผู้ใช้โดยไม่ต้องใช้รหัสผ่าน ซึ่งเปิดได้เฉพาะเมื่อตั้ง `DEMO_LOGIN=true` ค่าเริ่มต้นปิดอยู่ ระบบจริงต้องใช้ SSO ของโรงพยาบาลหรือรหัสผ่าน + MFA

## 3. Network และ Server

### 3.1 ขนาดงานที่ต้องรองรับ (ประมาณการ)

ตัวเลขข้างล่างเป็น**สมมติฐาน** ต้องยืนยันกับข้อมูลจริงของลูกค้า

| รายการ | 15 แห่ง (เริ่มต้น) | 30 แห่ง |
|---|---|---|
| คิวต่อวัน (สมมติ 3,000 คิว/แห่ง) | 45,000 | 90,000 |
| แถว `queue_tickets` ต่อปี | ≈16 ล้าน | ≈33 ล้าน (≈15–20 GB รวม index) |
| การเขียนช่วงพีค 08:00–10:00 (ออกคิว + เรียก + เสร็จ) | ≈5 ครั้ง/วินาที | ≈10 ครั้ง/วินาที |
| จอแสดงคิว (สมมติ 20 จอ/แห่ง) | 300 จอ | 600 จอ |
| ถ้าจอ polling ทุก 5 วินาที | 60 request/วินาที | 120 request/วินาที (เกือบทั้งหมดได้ "ไม่มีอะไรเปลี่ยน") |
| แถว `shifts` ต่อปี | ≈0.3 ล้าน | ≈0.65 ล้าน |

**ข้อสรุป:** งานเขียนข้อมูลมีน้อย ฐานข้อมูลเครื่องเดียวรองรับได้สบาย ส่วนที่หนักคือ**การอ่านซ้ำ ๆ จากจอแสดงคิว** จึงต้อง (1) ส่งข้อมูลแบบ push ผ่าน WebSocket แทนการ polling, (2) cache ข้อมูลที่อ่านบ่อยใน Redis และ (3) แยก replica ไว้ให้รายงานกับ dashboard อ่าน

### 3.2 Architecture เป้าหมายบน cloud

![Network และ server บน cloud](diagrams/network.svg)

**ทำไมออกแบบแบบนี้**

- **ทุก tier ของ app ไม่เก็บ state ไว้ที่เครื่อง (stateless):** session, cache และ job อยู่ใน Redis ทั้งหมด จึงเพิ่มหรือลดจำนวน container ได้ตามโหลดช่วงเช้า
- **WebSocket แยกเป็น tier ของตัวเอง:** API เขียนข้อมูลเสร็จก็ publish event เข้า Redis จากนั้น WebSocket ทุกตัวส่งต่อไปยังจอที่ subscribe channel ของโรงพยาบาลและแผนกนั้น เพิ่มจำนวนเครื่องได้โดยไม่ต้องใช้ sticky session ข้ามเครื่อง
- **ฐานข้อมูลไม่มี public IP:** เข้าถึงได้จาก subnet ของ app เท่านั้น ข้อมูลสุขภาพเป็นข้อมูลอ่อนไหวตาม PDPA มาตรา 26 ต้องเข้ารหัสทั้งตอนเก็บและตอนส่ง มี audit log และให้สิทธิ์เท่าที่จำเป็น
- **Backup + Point-in-time recovery:** เป้าหมายคือข้อมูลหายได้ไม่เกิน 5 นาที (RPO) และกู้ระบบกลับมาได้ภายใน 1 ชั่วโมง (RTO) ต้องตกลงกับลูกค้าอีกครั้ง
- **จอแสดงคิวต้องใช้ต่อได้ตอนเน็ตหลุดสั้น ๆ:** จอแสดงข้อมูลล่าสุดค้างไว้ พอต่อกลับได้ก็ดึงสถานะล่าสุดใหม่

**เลือก cloud:** ทั้ง AWS (ECS Fargate + RDS MySQL + ElastiCache) และ GCP (Cloud Run + Cloud SQL + Memorystore) ใช้ได้ทั้งคู่ เกณฑ์เลือก: (1) มี region ในไทยไหม เพราะข้อมูลสุขภาพอาจต้องเก็บในประเทศ ต้องตรวจสอบสถานะของแต่ละเจ้า ณ วันที่เลือก, (2) ทีมคุ้นกับเจ้าไหน และ (3) ราคาเทียบกับปริมาณงานจริง ตอนนี้ระบบรันเป็น container อยู่แล้ว (`docker-compose.yml`) ย้ายไปเจ้าไหนก็ได้

### 3.3 ขยายระบบเป็นขั้น

ขยายเมื่อตัวชี้วัดถึงเกณฑ์ ไม่ใช่ทำทุกอย่างตั้งแต่วันแรก

| ขั้น | เมื่อไหร่ | ทำอะไร |
|---|---|---|
| 0. ตอนนี้ | เดโม / pilot 1–2 แห่ง | VM เครื่องเดียว + docker compose, MySQL, backup รายวัน, CI/CD (มีแล้ว) |
| 1. ขึ้น cloud | ก่อนเปิดใช้ 15 แห่ง | Managed MySQL (Multi-AZ), Redis, API 2 ตัวขึ้นไปหลัง Load Balancer, worker แยก, monitoring + alert, WebSocket แทน polling |
| 2. ขยาย | ใกล้ 30 แห่ง หรือ CPU ของ DB > 60% ช่วงพีค | Autoscale ตาม CPU/latency, read replica ให้รายงาน, แบ่ง `queue_tickets` เป็น partition รายเดือน (ต้องยอมเอา foreign key ของตารางนี้ออก และใส่ `service_date` เข้าไปใน primary key ดู [LARGE-DATA.md ข้อ 1.11](LARGE-DATA.md)), archive ข้อมูลเก่าตามนโยบายเก็บข้อมูลของโรงพยาบาล |
| 3. เกินแผนเดิม | > 100 แห่ง หรือลูกค้าต้องการแยกฐานข้อมูล | แยกฐานข้อมูลเป็นกลุ่มโรงพยาบาล (shard ตาม `hospital_id`) หรือแยก DB ต่อรายสำหรับลูกค้าใหญ่ |

**ตัวชี้วัดที่ต้องดู:** latency p95 ของ API เรียกคิว (เป้า < 200 ms), CPU และจำนวน connection ของ DB, ความล่าช้าของ replica, ความยาวของ job queue, จำนวน WebSocket ที่เชื่อมต่ออยู่ และจำนวนครั้งที่ deploy แล้วล้ม

## 4. แผนย้ายจาก PHP/Laravel ไป Next.js + NestJS

### 4.1 ภาษาและเครื่องมือที่แนะนำ

ใช้ **TypeScript ทั้งระบบ** เพื่อให้หน้าเว็บกับ API ใช้ type ชุดเดียวกัน และทีมเดียวทำได้ทั้งสองฝั่ง

| ส่วน | ตอนนี้ (Laravel) | หลังย้าย | หมายเหตุ |
|---|---|---|---|
| หน้าเว็บ | React 19 + Vite ใน Laravel | **Next.js (App Router)** | ใช้ component เดิมได้เกือบทั้งหมด |
| API | Laravel controller + service | **NestJS** (module, controller, service) | โครงสร้างคล้าย Laravel มาก ย้ายทีละ module ได้ |
| ORM / migration | Eloquent + migration | **Prisma** (หรือ TypeORM) | ต้องให้มีระบบเดียวเท่านั้นที่เป็นเจ้าของ schema |
| Validation | Form Request | **class-validator** หรือ **Zod** | แชร์ schema กับหน้าเว็บได้ |
| Job / scheduler | Laravel Queue + Scheduler | **BullMQ** + `@nestjs/schedule` | ใช้ Redis ตัวเดิม |
| Real-time | Laravel Reverb | **Socket.IO** + Redis adapter | ใช้ channel ชื่อเดิม |
| Auth | Sanctum | **JWT / OIDC** (เช่น Keycloak) | ทั้งสองระบบต้องใช้ token ร่วมกันได้ในช่วงที่ยังย้ายไม่เสร็จ |
| สิทธิ์ | `Role` enum + Gate + middleware | **Guard + `@Roles()`/`@Permissions()` decorator** (หรือ CASL) | ย้าย map บทบาท×สิทธิ์เดิมไปเป็นไฟล์ที่ทั้งสองระบบอ่านร่วมกันได้ |
| ทดสอบ | PHPUnit (37 ข้อ, HTTP level) | **Jest** + Supertest, **Playwright** | ชุดทดสอบเดิมเป็น contract ที่ API ใหม่ต้องผ่าน |
| โครงสร้าง repo | repo เดียว | **monorepo** (pnpm + Turborepo): `apps/web`, `apps/api`, `packages/types` | type ของ API สร้างจาก OpenAPI |

### 4.2 วิธีย้าย: Strangler fig

ไม่เขียนใหม่ทั้งหมดในครั้งเดียว วาง reverse proxy ไว้ข้างหน้า แล้วค่อย ๆ ส่ง request ทีละ path ไปที่ NestJS พอย้ายครบก็ปิด Laravel

![Strangler fig](diagrams/strangler.svg)

### 4.3 ขั้นตอน

| ขั้น | งาน | เสร็จเมื่อ | ความเสี่ยง |
|---|---|---|---|
| 0. เตรียม (ทำใน Laravel) | สร้าง OpenAPI spec ของ API ทุกตัว, เปลี่ยนชุดทดสอบ HTTP ให้เป็น contract test ที่ยิงไป URL ไหนก็ได้, ย้าย logic ทั้งหมดเข้า service (ตอนนี้ทำแล้ว) | contract test ผ่านกับ Laravel | ต่ำ |
| 1. หน้าเว็บ → Next.js | ย้าย React เดิมเข้า Next.js ให้เรียก API Laravel ตัวเดิม | ผู้ใช้ไม่เห็นความต่าง, E2E (Playwright) ผ่าน | ต่ำ (ย้อนกลับได้ที่ DNS) |
| 2. วางโครง NestJS | monorepo, auth แบบใช้ token ร่วมกัน, reverse proxy, CI/CD, monitoring | request ทดสอบผ่าน proxy ไปถึง NestJS | ต่ำ |
| 3. ย้ายส่วนที่อ่านอย่างเดียว | สถิติ/dashboard, คิวของแพทย์ (`my-queue`), ข้อมูลอ้างอิง | contract test ผ่านกับ NestJS, latency ไม่แย่ลง | ต่ำ |
| 4. ย้ายจัดเวร | ตรวจกติกา, จัดเวรทั้งเดือนอัตโนมัติ, คำขอลา + อนุมัติ | ทดสอบจัดเวร 11 ข้อผ่าน และเทียบผลจัดเวรกับระบบเดิมด้วยข้อมูลจริงย้อนหลัง | กลาง (กติกาซับซ้อน) |
| 5. ย้ายคิว (ส่วนที่เสี่ยงที่สุด) | ออกคิว (lock counter), เรียกคิว (`SKIP LOCKED`), WebSocket | load test ช่วงพีคผ่าน, ไม่มีเลขคิวซ้ำ, ไม่มีคิวที่สองห้องได้พร้อมกัน | สูง → ย้ายทีละโรงพยาบาลด้วย feature flag |
| 6. job + ปิดระบบเดิม | สรุปยอดรายวัน, ลบข้อมูลเก่า → BullMQ, แล้วปิด Laravel | ไม่มี request ไป Laravel 2 สัปดาห์ | ต่ำ |

**ข้อควรระวัง**

- **ช่วงที่สองระบบใช้ฐานข้อมูลเดียวกัน ต้องมีระบบเดียวที่เป็นเจ้าของ migration** (เสนอให้ Laravel เป็นเจ้าของจนถึงขั้น 5 แล้วค่อยส่งต่อให้ Prisma ด้วย `prisma db pull`) ถ้าสองระบบแก้ schema พร้อมกัน ข้อมูลจะพังได้
- **ย้ายทีละ endpoint ต้อง rollback ได้ทันที:** แค่แก้ route ที่ proxy ไม่ต้อง deploy ใหม่
- **อย่าย้ายพร้อมเพิ่มฟีเจอร์:** API ใหม่ต้องให้ผลเหมือนเดิมก่อน ค่อยปรับปรุงทีหลัง
- **ไม่ต้องหยุดพัฒนาฟีเจอร์ระหว่างย้าย:** ฟีเจอร์ใหม่ให้เขียนใน NestJS ตั้งแต่ขั้น 2 เป็นต้นไป

### 4.4 สิ่งที่ควรเริ่มทำตั้งแต่ตอนนี้ (ยังเป็น PHP อยู่)

- ทำแบบ API-first: หน้าเว็บคุยกับระบบผ่าน JSON API อย่างเดียว ไม่ใช้ Blade render ข้อมูล (repo นี้ทำแบบนี้แล้ว)
- เขียน logic ไว้ใน service ไม่ใช่ใน controller (`QueueService`, `RosterService`) ย้ายแล้วเปลี่ยนแค่ภาษา โครงเหมือนเดิม
- ทดสอบที่ระดับ HTTP: ชุดทดสอบเดิมจะกลายเป็น contract ของ API ใหม่ รวมถึงทดสอบสิทธิ์ทุกบทบาท
- ตั้งชื่อ channel ของ event ให้เป็นมาตรฐานตั้งแต่ตอนนี้ เช่น `hospital.{id}.dept.{id}`
- เก็บ config ไว้ใน env และ build เป็น container ทั้งหมด

## 5. ข้อเสนอฟีเจอร์ถัดไป

ข้อเสนอในส่วนนี้**ยังไม่ได้ทำในโค้ด** ออกแบบให้ต่อยอดจากของเดิมได้โดยไม่ต้องรื้อ ขนาดงานเป็นการประเมินคร่าว ๆ สำหรับนักพัฒนา 1 คน (S = 1–3 วัน, M = 1–2 สัปดาห์, L = มากกว่า 2 สัปดาห์) ส่วนตัวเลขนโยบายการลาทุกตัวเป็นค่าตัวอย่างที่ตั้งได้ต่อโรงพยาบาล **ต้องยืนยันกับ HR ของแต่ละแห่ง** เพราะโรงพยาบาลรัฐใช้ระเบียบการลาของข้าราชการ ส่วนโรงพยาบาลเอกชนใช้กฎหมายคุ้มครองแรงงานและข้อบังคับของบริษัท

### 5.1 ให้ HR เป็นผู้อนุมัติการลา (อนุมัติ 2 ขั้น)

หัวหน้าแผนกรู้ว่าการลากระทบเวรแค่ไหน ส่วน HR รู้สิทธิ์การลาและระเบียบ จึงเสนอให้แยกเป็น 2 ขั้น: **หัวหน้าแผนกเห็นชอบ → HR อนุมัติ** คนที่จัดเวรกับคนที่อนุมัติสิทธิ์จะเป็นคนละคน (separation of duties) ส่วนโรงพยาบาลเล็กเลือกใช้แบบขั้นเดียวเหมือนตอนนี้ได้

| เรื่อง | ตอนนี้ | ข้อเสนอ |
|---|---|---|
| บทบาท | แอดมิน (หัวหน้าแผนก) อนุมัติเอง | เพิ่ม role `hr` · หัวหน้าแผนกเปลี่ยนจาก `leave.approve` เป็น `leave.endorse` (เห็นชอบ) |
| สิทธิ์ใหม่ | – | `leave.endorse` (หัวหน้าแผนก, เฉพาะแผนกตัวเอง) · `leave.approve` (HR, ทุกแผนก) · `leave.policy.manage` และ `leave.balance.adjust` (HR) |
| สถานะ | `pending → approved / rejected` | `pending → endorsed → approved` · ปฏิเสธได้ทั้งสองขั้น · เพิ่ม `cancelled` |
| ตั้งค่าต่อโรงพยาบาล | – | `leave_approval_flow = single / two_step` |
| คำขอค้างนาน | – | ค้างเกิน 48 ชม. (ตั้งได้) แจ้งเตือนผู้อนุมัติซ้ำ · ถ้าวันลาใกล้แล้วแจ้งผู้อนุมัติสำรอง |
| ตาราง | `staff_unavailabilities` | เพิ่ม `endorsed_by`, `endorsed_at`, `leave_type_id`, `start_date`/`end_date`, `half_day`, `attachment_path` |

![BPMN ข้อเสนอ: ลา 2 ขั้น หัวหน้าแผนก → HR](diagrams/bpmn-leave-proposal.svg)

ขนาดงาน: **M** · ต่อยอดได้จาก `LeaveController` และ `App\Enums\Role` ที่มีอยู่ ชุดทดสอบสิทธิ์เดิมขยายเพิ่มได้ตรง ๆ

| `attachment_required_after_days` | ต้องแนบเอกสารเมื่อลาเกินกี่วัน | – | 3 วัน (ใบรับรองแพทย์) | – |
| `allow_half_day` | ลาครึ่งวันได้ไหม | ได้ | ได้ | ได้ |
| `counts_toward_balance` | หักวันคงเหลือไหม | หัก | หัก | หัก |

**ตัวเลขในตารางเป็นค่าตัวอย่าง ไม่ใช่ข้อกฎหมาย**

**ต้องตกลงกับ HR ก่อนทำ**
- **นับวันแบบไหน:** นับเป็นวันทำการหรือวันปฏิทิน แพทย์ที่อยู่เวรวันหยุดควรนับแบบไหน
- **ลาฉุกเฉิน:** ถ้ามีเหตุฉุกเฉินจนแจ้งล่วงหน้าไม่ทัน ให้ HR อนุมัติข้ามกติกาได้ แต่ต้องใส่เหตุผลและเก็บไว้ใน audit log
- **ใบรับรองแพทย์:** เป็นข้อมูลสุขภาพที่อ่อนไหวตาม PDPA ต้องเก็บใน object storage แบบเข้ารหัส และให้เฉพาะ HR เปิดดูได้

ขนาดงาน: **M**

### 5.3 วันลาคงเหลือ

แสดงวันลาคงเหลือในฟอร์มก่อนกดส่ง และไม่ให้ส่งถ้าวันลาไม่พอ หรือยอมให้ติดลบตามนโยบาย เสนอให้เพิ่มตาราง `leave_balances` แยกตามแพทย์ × ประเภทการลา × ปี

| คอลัมน์ | ความหมาย |
|---|---|
| `entitled` | สิทธิ์ของปีนั้น (คำนวณตามสัดส่วนสำหรับคนที่เข้างานกลางปี) |
| `carried_over` | ยกมาจากปีก่อน (ไม่เกิน `carry_over_max_days`) |
| `reserved` | กันไว้สำหรับคำขอที่ยังรออนุมัติ |
| `used` | ใช้ไปแล้ว (อนุมัติแล้ว) |
| คงเหลือ | `entitled + carried_over − used − reserved` |

**วงจรของวันลา:** ส่งคำขอ → ย้ายเข้า `reserved` · ไม่อนุมัติหรือยกเลิก → คืนจาก `reserved` · อนุมัติ → ย้ายจาก `reserved` ไป `used` · ยกเลิกหลังอนุมัติ (ถ้านโยบายอนุญาต) → คืนจาก `used`

**ข้อควรระวัง**
- **กันแพทย์ส่งคำขอพร้อมกันจนวันลาติดลบ:** ล็อกแถว balance ใน transaction เดียวกับการบันทึกคำขอ แบบเดียวกับที่ใช้ล็อกเลขคิวใน `QueueService::issue()`
- **ปรับยอดด้วยมือ:** HR ปรับยอดเองได้ แต่ต้องใส่เหตุผลและเก็บใน audit log
- **ขึ้นปีใหม่:** มี scheduled job ยกยอดวันลาไปปีถัดไป (`schedule:run` เหมือนงานสรุปยอดคิว)

**API ที่ต้องเพิ่ม**
- `GET /staff/{staff}/leave-balances?year=` ดูวันคงเหลือ
- `POST /leave-balances/{balance}/adjust` HR ปรับยอด
- `GET /leave-types`, `PUT /leave-types/{type}` HR ตั้งค่าประเภทการลา

ขนาดงาน: **M**
